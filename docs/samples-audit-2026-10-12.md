## 已确认的专项调查

### 多行注释被转义标记污染（0062、0065、0285）

0062 `媒体播放/MP3播放器.e` 的 `MP3信息类` 与 0065 `常用工具/文件批量更名工具/E-F_RENAME.e` 的 `MP3标签功能实现`，均含三行 ID3v2 英文注释。只追加页尾注释后，语义回包将 `#e2txt_body_line#`、`#e2txt_text#` 和字面量 `\r\n` 写入注释。再次拆包又包一层转义标记。

已使用 AutoLinker `read_real_file` 独立读取 0062 原件副本及 Win32 回包件：两者都能打开；原件显示正常多行注释，回包件显示内部标记，故不是单纯 Diff 排版误报。未执行该样本程序，也未据此宣称编译通过。0285 `行业应用/翠薇书店管理系统 V1.0/书店管理系统.e` 的连接说明注释也出现同类转义污染；不同架构是否进入该阶段，以逐例 CSV 为准。

证据：`D:/test/samples-ide62-original-20261012/evidence.json`、`D:/test/samples-ide62-edited-20261012/evidence.json`。修复应统一源码语义入口与旧恢复入口的正文转义协议，不能删掉这些注释掩盖差异。

### 窗口实例引用回读错误（0069，Win32）

`常用工具/易容大师/ecom_src/anchors/example.e` 首次拆包为 `_启动窗口.宽度 ＝ 400`、`_启动窗口.高度 ＝ 300`。追加注释并回包后，IDE 真实代码仍引用 `_启动窗口`，但再次拆包文本变成 `窗口1`。

直接再次回包未编辑的目录会复用快照，IDE 引用仍正确；这不足以证明第二次语义构建正确。因此另复制该目录、再次追加注释强制语义重建，IDE 真实代码随即变成 `窗口1.宽度 ＝ 400`、`窗口1.高度 ＝ 300`。这是解码产生错误文本并在后续编辑时传播为语义变化的问题，不能归为窗口改名排版。

证据：`D:/test/samples-ide69-original-20261012/evidence.json`、`D:/test/samples-ide69-edited-20261012/evidence.json`、`D:/test/samples-ide69-second-20261012/evidence.json`、`D:/test/samples-69-second-semantic-20261012/result.json`。下一步应排查窗口实例、窗口程序集和导入模块声明的 ID／名称映射。

### x64 解码与写入的交叉验证

0026、0034 原生 x64 流程因 `type_id_resolution_failed` 失败。使用同一样本已经加注释的 Win32 工作目录，交给 x64 写入，再用 Win32 拆包，两例均成功且内容一致。这说明这两例的失败与原生 x64 缺少支持库元数据有关，不能直接断言 x64 写入器都失败。

证据：`D:/test/samples-x64-writer-check-20261012/0026/result.json`、`0034/result.json`。

0063 原生 x64 回包后窗口 XML 丢失子控件；改用 Win32 解码该 x64 产物仍存在差异，因此该例不只是 x64 回读显示问题。证据：`D:/test/samples-x64-controls-20261012/result.json` 及同目录差异文件。

### 缺失依赖与已找到的 NPK 不可混淆

0025 缺 `eAPI`，出现 `_Lib9*` 和 `type_id_resolution_failed: 0xA000A`。IDE 原件副本的 MCP 对照在等待期内未进入可读状态，该尝试不能用来证明原件已损坏。

0168 等短信控件样本的 `.npk` 已在副本中找到（例如 `TransoftSMSControl30.npk`），但仍报 `window_control_type_metadata_unavailable`。0288 等 Grid++report 样本则缺 `gregn45.npk`，部分还缺 `grdes45.npk`。必须区分“依赖文件缺失”与“依赖存在但不具备可用类型元数据”；这些日志本身不是工作进程崩溃证据。

## 修复优先级与判定边界

1. 优先修复真实内容变化：多行注释转义污染、窗口实例解码映射，以及 x64 丢失嵌套控件。0069 已证明“文件可打开、首次回包甚至二次快照回包成功”仍可能掩盖下一次编辑时的引用变化。
2. 支持库元数据应统一进入语义解析和窗口重建。x64 的跨进程桥接不能只覆盖属性编解码，还需解决命令、类型、常量等元数据的完整可用性；不能靠把未解析类型改成 0 或跳过控件来宣称成功。
3. `.ec` 匿名事件处理器身份需单独调查。当前证据只能确认回包器无法解析处理器，未独立证明原件已损坏，不能直接归类为“用户原代码写错”。
4. 大窗口工程需调查控件工作进程的重复启动和缓存粒度；延长审计时限只用于区分慢与失败，不是性能修复。

本轮只改进审计脚本与记录，没有修改 C++ 实现或用特殊分支绕过失败。本报告中的“严格通过”是拆包／回包及内容检查口径，不等于 IDE 编译通过；IDE 对照使用 `read_real_file` 读取真实页面，未运行样本程序。
