# 工程内符号缓存性能优化

本轮基线为上一轮源码、支持库和窗口优化后的版本。继续将重复查询改成哈希索引，并复用工程内的解析结果。未提交 Git；用户下载的原工程保持不动。

## 实现和缓存生命周期

- `SymbolResolver` 的 `m_callableNames` 用 `std::unordered_set` 保存原始 DLL/子程序名称。支持库命令每次判断是否需要限定库名时，直接查询集合，替代完整扫描 DLL 和子程序表；保留原始名称的比较规则。
- `m_rawTypeNames` 保存原始程序集/结构名称，加速支持库类型的重名判断；与经过匿名命名、同名消歧后的显示名称集合分开，保留原有语义。
- `m_resolvedTypeNames` 用 `std::unordered_map` 按类型 ID 保存最终类型名。同一类型多次用于参数、局部变量、成员、XML 和快照时，复用结果；缓存包含空结果。
- 同一工程的源码、全局变量、数据类型、DLL 声明、常量、窗口 XML、公开头和原生快照共用一个解析器，复用符号索引和支持库元数据。匿名类型提示也只计算一次，避免重复读取依赖模块。
- 源码阶段结束后显式清除当前子程序和局部名称上下文，防止共享解析器把最后一个子程序的作用域带入声明和窗口处理。
- 解析器属于当前 `ModuleSections`，生成结束立即释放；每个依赖模块独立创建，不跨工程、跨命令缓存，不缓存控件实例，也不保存支持库 DLL 的裸指针。

空间开销随当前工程的不同名称数和不同类型 ID 数增长，重复引用只查已有条目。共享解析器同时省去了各阶段反复构建索引和加载元数据的工作，不需要预留大块固定缓存或引入新依赖。

阶段日志中，`build_bundle/prepare_symbols` 记录匿名类型提示和解析器的统一准备；原先分散在各阶段中的构造成本已移到这里。因此比较 `source_pages` 时，还应同时检查准备时间和整体耗时。

## 用户工程：完整解包

使用 `temp/user-manager-test-6a3a46fe/1 - 管理器 - 95-1.e` 副本。普通 `unpack` 包含依赖；同架构优化前后交替三轮，不同架构的耗时不作速度排名。

| Release | 优化前 3 轮，秒 | 优化后 3 轮，秒 | 平均耗时变化 |
| --- | --- | --- | --- |
| Win32 | 9.023 / 9.851 / 8.948 | 8.204 / 8.055 / 8.314 | 9.274 → 8.191，减少 11.7% |
| x64 | 8.012 / 9.117 / 8.566 | 7.809 / 7.671 / 8.717 | 8.565 → 8.066，减少 5.8% |

| 主工程阶段，三轮平均 | Win32 优化前 → 后 | x64 优化前 → 后 |
| --- | --- | --- |
| 源码还原 `source_pages` | 0.422 → 0.124 秒 | 0.481 → 0.168 秒 |
| 声明 `declarations` | 0.0532 → 0.0025 秒 | 0.0508 → 0.0013 秒 |
| 新增统一准备 `prepare_symbols` | 新版 0.0422 秒 | 新版 0.0338 秒 |

源码阶段耗时分别减少约 71% 和 65%。完整工程剩余耗时主要在窗口属性，本轮保留原有控件处理流程。x64 新版第三轮 `write_bundle` 为 1.188 秒，前两轮为 0.688 / 0.552 秒；该轮未从均值中排除，写盘波动的系统原因未经验证。

主工程和依赖产物逐轮比较相对路径及 SHA-256：Win32 每轮 298 个、x64 每轮 287 个产物完全一致，包括 175 个主工程源码/XML 文件；仅排除工作区随附的打包器 EXE。各架构原本导出的支持库说明数量不同，同架构优化前后保持一致。每轮仍只有一个属性辅助进程，无请求失败。

逐轮比较 `support_command_unresolved` 的完整诊断集合，两架构的每轮均保留原有 6 项，库、命令、子程序及原因信息一致，没有因缓存而隐藏报错。

原始报告：`temp/window-benchmark-67ea5b4be5/report.json`。

## 内存

基准脚本通过 Windows `GetProcessMemoryInfo` 读取每次运行的主进程峰值，表内为三轮平均，单位 MiB（1024² 字节）。辅助进程不计入这些数字。

| Release | 峰值工作集，优化前 → 后 | 峰值提交量，优化前 → 后 |
| --- | --- | --- |
| Win32 | 132.62 → 132.78 MiB | 121.79 → 121.36 MiB |
| x64 | 152.30 → 152.28 MiB | 148.22 → 148.02 MiB |

本样例主进程峰值内存基本持平。新增缓存占用部分内存，但减少重复构建、共享同一解析器抵消了部分开销；不能据此保证所有规模工程的内存变化都相同。

## 验证

证据路径除另有说明外均位于 `temp/cache-perf-20261017/`：

- Release Win32、x64 均编译成功，无编译警告或错误：`build-Win32.log`、`build-x64.log`。
- 两架构各 9 项编辑回包、真实易语言编译运行和再次解包检查通过；x64 测试实际使用 x64 解包器。覆盖局部/全局/控件/菜单重名、跨窗口引用、隐式窗口方法及属性，并保留类型错误诊断：`symbols-Win32/results.json`、`symbols-x64/results.json`。
- 支持库命令与同名 DLL 调用身份、双架构原生/文本元数据回包一致性验证通过：`support-command.log`。
- 方法作用域、类与程序集身份、同名用户方法与支持库命令、对象接收者验证通过：`function-scopes.log`。
- 全局变量、结构、DLL、前向调用和局部遮蔽的声明语义回包验证通过：`semantic-declarations.log`。
- 用户工程与精易模块在两架构原样解包/回包，共 4 项逐字节和 MD5 比较通过：`native-roundtrip/results.json`。
- 原始下载工程 SHA-256 复核未变：`ae6fced302ad4e5396a1366e14c81a45a71d90fe8058ea82d1f9b3a689c8deb1`。

用户工程的外部模块缺失和 eGrid 版本不匹配仍是既有环境问题；本轮不宣称用户完整工程编辑后可编译。未执行全量样本测试。

## 复现

基线二进制保存在 `temp/cache-perf-20261017/before-{Win32,x64}/`。

```powershell
python tools/BenchmarkWindowUnpack.py --before-root temp/cache-perf-20261017 --architecture both --rounds 3 --input 'temp/user-manager-test-6a3a46fe/1 - 管理器 - 95-1.e'
python tools/BenchmarkWindowUnpack.py --before-root temp/cache-perf-20261017 --architecture both --rounds 3 --input temp/core-perf-20261017/jingyi.ec --main-only
```

基准报告包含逐轮时间、阶段日志、产物数量、主进程峰值工作集和峰值提交量。每次解包都是独立进程，收益来自当前工程内复用。
