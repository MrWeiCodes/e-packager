# Win32 审计修复与全量复测（2026-10-12）

本记录接续 [首次审计](module-roundtrip-audit-2026-10-12.md)。原始审计证据不覆盖；修复后的最终全量结果见本文末尾的机器统计及配套 CSV、JSON。

## 实现变更

### 控件支持库调用隔离与 DLL 生命周期

ID 0339、0341、0353 的 `组件调用测试.e` 原先在拆包结束销毁宿主窗口时退出 `0xC000041D`。调试器先捕获到 `0xC0000005` 执行异常：窗口回调地址位于 `PAGE_READWRITE` 私有堆，地址上的内容为动态生成的 x86 指令。调用栈经过 USER32 的窗口消息派发，最终回到 `BuildFormXmlEntries`。栈和现场见 `D:\test\win32-fixes-20261012\crash-stack2.txt`。

复用现有 CBOR 工作进程桥接，让 Win32 的属性解码、属性更新和事件查询也在独立进程运行；Win32 启动当前 EXE 的内部 worker，x64 继续使用 Win32 helper。显式 `InProcess` 模式只供 worker 和 ABI 测试使用，避免递归启动 worker。失败保留退出码，超时单独报告，工作进程禁用系统错误弹窗。

删除在 `DONT_RESOLVE_DLL_REFERENCES` 映射上调用 `GetNewInf`、随后反复卸载/初始化的流程。`GetNewInf` 本身是 DLL 代码，依赖导入表和初始化状态，不能当作纯数据读取。现在工作进程正常加载 DLL，在本次操作及控件销毁期间保持库有效，进程退出释放。

拆包无法读取专属属性时，保留原有扩展属性字节并发出 `control_property_decode_failed`，包含窗口、控件、类型及 worker 错误。需要更新这些属性的语义回包则返回错误，不将工作进程崩溃当作成功。**这解决了主进程被支持库带崩的问题，未修复旧支持库自己生成不可执行回调的行为。** 这三个样本仍不能完成语义回包。

没有关闭主进程 DEP，没有改变任意堆页执行权限，没有按 DLL 文件名、样本编号或指令字节打补丁。Windows 默认堆不可执行及动态代码应使用相应执行权限的依据见 [Microsoft DEP 文档](https://learn.microsoft.com/en-us/windows/win32/memory/data-execution-prevention)。

### 删除重复的字符串类型推断

`SourcePreflightValidator` 的旧赋值检查把以 `到数值 (` 开头、以 `)` 结束的整段表达式视为数值，因此误判：

```text
retBool ＝ 到数值 (zyW2A (v1)) ＝ 到数值 (zyW2A (v2))
```

删除旧的前后缀推断、重复类型枚举及仅为其服务的辅助函数；结构/声明检查保留，赋值语义统一交给 `SourceSemanticValidator` 的表达式 AST。真实类型不匹配和跨方法局部变量引用仍被拒绝，错误信息增加目标/来源类型。没有按函数名或样本豁免校验。

ID 0282、0477、0482 因此恢复语义回包。0478–0481 的比较误报解除后暴露出更后面的 `if_true_end_invalid`，不计作恢复成功。

### 声明级注释进入原生备注字段

`ParseProgramPage` 将子程序之外的独立注释保存到最近的程序集/程序集变量声明备注；原生字段使用 CRLF 分隔首行备注与后续独立注释。导出时首行仍在声明最后一列，后续行独立输出；空首行不生成额外逗号列。没有附加隐藏方法或私有侧车格式。

覆盖空程序集、空类、已有备注、已有程序集变量和多行注释；连续两次语义回包仍保留注释。原生格式不独立保存这类行的位置，空白行位置可能规范化；具有方法的页尾注释仍由方法体处理。

### 声明索引复用

方法重建之前声明已经全部分配 ID，但旧实现仍为每个方法重复遍历所有类、方法、成员、常量、窗口、DLL，WPS 样本因此超过原 90 秒测试上限。

现在每个程序集/类建立一次索引，类内方法复用；每次方法只重置词法变量表，再覆盖参数及局部变量。不会跨方法残留局部变量，方法体仍走原来的语义编码，没有启用旧字节码兜底。项目声明索引目前是每个类一份，并非整个工程仅一份。

ID 0321 先前独立复现约 147.047 秒；本次定向语义回包约 10.997 秒，第一轮四任务并发全量中约 12.593 秒。不同运行负载下的数值仅作观测，不作为固定性能保证。

### 窗口类型和库限定成员

无关联程序集的窗口仍应继承核心窗口的方法和属性。修复符号索引中的 `form → classId=0` 断链，直接连接到核心窗口类型；有程序集的窗口仍保留原继承链。ID 0188 `PopWindow.e` 的 `winMain.销毁()` 恢复。

支持库类型成员同时登记非限定名和正确库限定名，文本元数据和原生 FNE 元数据路径保持一致；语义校验同步登记限定成员。`窗口.krnln::销毁()` 可解析，`窗口.missing_library::销毁()` 仍被拒绝，不通过简单剥前缀绕过所属库校验。

ID 0036 虽有 `krnln::销毁()`，但该工程没有对应窗口 XML/对象绑定，仍失败；不根据“窗口程序集”字样凭空补窗口对象。

## 尚未解决的问题

- 缺失历史绝对路径或相对路径的 `.ec` 依赖仍报错，不伪造模块。
- `_Lib*` 与缺库的逐项对应见最终证据 JSON；缺失支持库需要补齐正确版本，不能猜命令编号或用其他库替代。
- 旧控件支持库的 DEP 回调故障仅完成隔离，专属属性仍无法可靠读取/修改。
- 匿名类型身份、父对象调用和其他特殊方法/类型仍有语义建模缺口，未重新启用字节码复用来绕过。
- ID 0421 存在名为“窗口”的普通程序集，与核心“窗口”类型的命名空间冲突，仍需把程序集作用域与实例类型符号分离；本轮未用样本名特判。
- ID 0233、0478–0481 的 `if_true_end_invalid` 已追到注释化的 `.如果真` 块：导出的注释行保持相同缩进，恢复器去掉注释前缀后仍按缩进解析结构化流程，提前结束块。这属于注释/禁用流程表示的解析缺口，不能归为普通“源码语法错误”。修复需要区分纯文本注释与禁用的结构化流程，避免把后者的未注释子语句错误激活。
- 依赖版本导致的签名不匹配等仍需对照真实 IDE 逐项确认，不能把全部预检错误归为坏源码。
- 部分源码运算符和字节集字面量的空格会规范化；严格文本比较仍如实报告。
- 第一轮复测中 ID 0217、0416、0417 的资源索引指向的驱动 `.bin` 在文件系统中缺失，回包报 `read_image_list_failed`。没有取得删除者证据，不能断言是杀毒软件；未修改安全软件设置或从快照绕过缺失资源。
